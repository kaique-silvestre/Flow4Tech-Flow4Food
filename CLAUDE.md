# Flow4Tech: sistema de gestao

Modular monolith. .NET backend, two React front apps (`app`, `control`) plus a shared design-system package. Planning docs: `.scratch/S-00-novo-sistema/`; current spec: `.scratch/S-01-fundacao-tecnica/spec.md`.

## Structure
- `backend/Flow4Tech.sln`
  - `src/Kernel`: small stable shared code (organization/unit context, `Money`, `EntityId`, `IClock`; `Events/IDomainEvent`; `Authorization/IAuthorizationEngine`: the single decision interface, ADR-006; `Audit/`: `IAuditLog`, `AuditEntry`, `ITechnicalLog`, the secret rule `SensitiveData`, `Correlation`).
  - `src/<Module>/{Domain,Application,Infrastructure,Interface}`: one folder per module (`Organizacao`, `Permissoes`, `Identidade`). Project names `Flow4Tech.<Module>.<Layer>`.
  - `src/Infrastructure/Data`: shared technical data access (`Flow4Tech.Infrastructure.Data`: `TenantDatabase`, `MigrationRunner`); not a module; only a module's Infrastructure layer (and Api) may reference it.
  - `src/Infrastructure/Outbox`: transactional outbox and background-job seam (`Flow4Tech.Infrastructure.Outbox`: `OutboxWriter`, `OutboxDispatcher`, `OutboxSweeper`, `IOutboxConsumer`, `IdempotentConsumer`, `IBackgroundJobs`); not a module, built on `TenantDatabase`; module Infrastructure layers may reference it.
  - `tests/Authorization`: authorization engine contract (profile x permission matrix, cases 1-3, deny precedence), the factory policy and the cumulative-limit concurrency test against real PostgreSQL (classes named `*Integration*`).
  - `tests/Organizacao`: layered settings (ticket 10): pure resolution, option declaration and value rules, and the service against real PostgreSQL (inheritance, lock, history, restore, start instant, permission, audit, RLS, append-only; classes named `*Integration*`).
  - `src/Infrastructure/Audit`: audit trail and technical log (`Flow4Tech.Infrastructure.Audit`: `PostgresAuditLog`, `AuditChainVerifier`, `AuditJobs`, `TechnicalLog`); not a module, built on `TenantDatabase` and the outbox; registered by `AddAuditoria()`.
  - `src/Infrastructure/Migrator`: deploy-time console (`Flow4Tech.Migrator`, `dotnet Flow4Tech.Migrator.dll`): applies `backend/migrations` with the OWNER credential, gives `flow4tech_app` its login, verifies the app credential is restricted; Npgsql stays in Data (`DatabaseUrl`, `AppRole`). Never run by the web app.
  - `src/Api`: host (`Flow4Tech.Api`, Web SDK); health endpoints; binds to `PORT` (8080 fallback), maps `DATABASE_URL`.
  - `tests/Flow4Tech.Tests`: xUnit. `tests/Isolation`: tenant isolation + RLS architecture tests against real PostgreSQL (classes named `*Integration*`). `tests/Outbox`: outbox, dispatcher, idempotent consumer and job-context tests against real PostgreSQL. `tests/Audit`: audit trail, chain verification, concurrency, secret rule and technical log against real PostgreSQL. `DoisTenantsEndpointsTests` (in `Flow4Tech.Tests`): two organizations through the real authenticated route (login, units, sessions, settings, profiles, invitations, accounts, audit, table sweep).
  - `backend/migrations`: versioned plain SQL (`NNNN_name.sql`), see Data and tenant isolation.
- `frontend/{app,control,design-system}` and `frontend/packages/api-client` (generated TypeScript client, imported by `app` and `control`): pnpm workspaces (listed in root `pnpm-workspace.yaml`); `frontend/tsconfig.base.json` is strict.
- `docs/tickets.md`: índice de tickets `F4-NNNN` (ID, spec, ticket, branch, PR, status); regras de branch/commit/PR em "Branches, IDs e PRs" abaixo e no ADR-016.
- `docs/adr/`: decisions; copy `0000-template.md`. Platform base: 002 RLS, 003 outbox, 005 identity, 006 authorization (incl. persisted rules), 009 hosting, 010 sessions, 011 login protection, 012 invitations/recovery/Google, 013 layered settings.

## Commands (run from repo root)
- build: `dotnet build backend/Flow4Tech.sln`
- test: `dotnet test backend/Flow4Tech.sln` (needs Docker running: integration tests start PostgreSQL via Testcontainers; front tests are `pnpm -r --if-present test`)
- test without Docker (cloud sessions): the integration fixtures (`Isolation/PostgresFixture.cs`, and the per-class `*EndpointsDatabase` fixtures in `Flow4Tech.Tests`) were swapped TEMPORARILY for a local PostgreSQL 16 (superuser, one fresh database per fixture; the cluster needs `GRANT flow4tech_app TO flow4tech_owner WITH ADMIN OPTION`), run one suite at a time with `-m:1`, and the swap was reverted, never committed. This proves the logic, not the Testcontainers path (`postgres:17-alpine`).
- typecheck: `dotnet build backend/Flow4Tech.sln` (nullable + strict analyzers, warnings are errors) and `pnpm install && pnpm -r typecheck`
- lint/format: `dotnet format backend/Flow4Tech.sln` (add `--verify-no-changes` to check only); front: `pnpm lint` (Biome, check only, same as CI) and `pnpm lint:fix` (applies format and safe fixes). Config `biome.jsonc` at the root, covers `frontend/**` except the generated `schema.ts`.
- dev: `docker compose up --build` (PostgreSQL + API; `docker compose down` to stop)
- port: API `http://localhost:8080` (`GET /health/live`, `GET /health/ready`), PostgreSQL `localhost:5432` (user/password/db `flow4tech`)
- contract: after changing any API route/DTO, regenerate and commit both outputs: `dotnet build backend/src/Api/Flow4Tech.Api.csproj -p:GenerateContract=true` (writes `backend/src/Api/openapi.json`) then `pnpm --filter @flow4tech/api-client generate` (writes `frontend/packages/api-client/src/schema.ts`, never edit by hand). Give every route a stable `.WithName("...")` (becomes the operationId) and typed responses (`TypedResults`/`.Produces<T>()`).
- client tests: `pnpm -r --if-present test`
- config: environment variables only: `Flow4Tech__Tokens__AppKey` (required outside Development/Testing), `PORT`, `ConnectionStrings__Default` or Railway-style `DATABASE_URL` (application credential); migrator: `MIGRATION_DATABASE_URL` or `ConnectionStrings__Migration` (owner), `APP_DB_PASSWORD`, `MIGRATIONS_DIR`, `SKIP_APP_CHECK` (opt-out, never in staging/production); the API reports `GIT_SHA` as `commit` in `/health/ready`.
- backup: production has NO database backup (Railway Pro not subscribed; owner decision 2026-11-07, F4-0098, `docs/runbooks/backup-e-restauracao.md` with the triggers to revisit). Take a manual `pg_dump` before any risky production change.
- deploy: Railway (API + PostgreSQL, project `flow4tech-v2`) and Vercel (front), see `docs/runbooks/deploy.md` and ADR-009. Railway's GitHub integration deploys `dev-v2` -> `staging` and `main-v2` -> `production` by itself after the `ci` checks pass ("wait for CI"); there is no deploy workflow. Service settings (source, wait for CI, Dockerfile, pre-deploy migrator, healthcheck) are code in `.railway/railway.ts`: it is NOT read at deploy time, apply it per environment with `railway config plan` then `railway config apply`; `railway.toml` is dead (ignored for new services). Variables and secrets live only in Railway. Migrations run in the pre-deploy command with the OWNER credential; local dev (`docker compose up --build`) uses the same two credentials: `migrate` as owner, `api` as `flow4tech_app`.

Merge requires the aggregate job `gates` to be green (branch protection); Deploys are Railway's, not a job here.

A new screen needs a scan there. Axe finds about a third of the real accessibility problems (no keyboard-flow or screen-reader judgement).

Pure rules, no Docker, run in the same jobs as their project's unit tests. Generators go in a `*Geradores` static class (`[Property(Arbitrary = [typeof(...)])]`); a failure prints the shrunk counterexample. Each property was checked by planting a bug in the rule (mutation by hand) and seeing it fail. A bill-splitting function does not exist yet (F4-0061): add its properties (parts sum to total, difference at most 1 cent) when it lands.
- `mutation-tests` (informational, not in `gates`, F4-0106): Stryker.NET 5.0.0 (`.config/dotnet-tools.json`, `dotnet tool restore`) plants bugs in the pure domain code and reports how many the no-Docker tests catch. - `isolation-tests`: `backend/tests/Isolation` (tenant isolation + RLS architecture rule, real PostgreSQL via Testcontainers, app credential). Own project, so the `unit-tests`/`integration-tests` name filters (which target `Flow4Tech.Tests` only) neither run nor miss it.

- `audit-tests`: `backend/tests/Audit` (append-only privileges, hash chain, tamper detection with the OWNER credential, concurrent writers, secret rule, technical log; real PostgreSQL via Testcontainers). Own project, same reason as isolation.
- `identidade-tests`: `backend/tests/Identidade` (sessions, rotating refresh, reuse, revocation triggers and the access token, Argon2id vs the RFC 9106 vector, k-anonymity breach check, accounts, owner protection, login without enumeration, pre-authentication functions and the RLS exception, real PostgreSQL via Testcontainers). Own project, same reason as isolation.
- `organizacao-tests`: `backend/tests/Organizacao` (layered settings on real PostgreSQL via Testcontainers). Own project, same reason as isolation.
- `authorization-tests`: `backend/tests/Authorization` (engine contract on every engine, daily-cap concurrency under RLS on real PostgreSQL via Testcontainers, app credential). Own project, same reason as isolation.
- `architecture-tests` also runs the route permission gate (`RoutePermissionTests`, ticket 10): every route declares a catalog permission, unknown permission fails, catalog export `backend/permissions.catalog.txt` must match. It is the permission gate; there is no separate job.

Duration budget (TARGET, not yet measured; replace with the first real run): whole pipeline <= 10 min wall clock, each job <= 5 min (integration <= 8 min). Local reference: build ~10 s, integration tests ~20 s with warm Docker.

## Module-boundary rules
- Layers: Domain -> Kernel only; Application -> Domain; Infrastructure and Interface -> Application. Never the reverse.
- A module may use another module only through its public API (Application contracts) or its events. Never reference another module's Domain, Infrastructure or Interface.
- Kernel stays small; do not put business rules in it.
- Enforced by `backend/tests/Architecture` (runs in `dotnet test`): forbidden edges, cycles, another module's internals (csproj refs and `using`), and Domain referencing packages, frameworks, or outer layers all fail the build.
- Declare a new allowed edge: add the target to the source module's list in `backend/modules.dependencies.json` (`"Permissoes": ["Organizacao"]` = Permissoes may reference `Organizacao.Application`; this file is the only source of truth). Then add the `ProjectReference` to `Flow4Tech.Organizacao.Application` from Permissoes' Application/Infrastructure/Interface project (never Domain). Cycles stay forbidden; a new module must be added to the file too.

## Conventions
- Money: integer cents plus currency (`Money`). Never float/decimal for stored amounts.
- Time: UTC only, via injected `IClock`; do not call `DateTime.UtcNow`/`DateTimeOffset.UtcNow` in domain code.
- Ids: UUID v7 (`EntityId.New()`).
- Data: plain Postgres, EF Core with SQL kept visible and testable (schema and RLS are SQL migrations; see Data and tenant isolation). Config by environment variables; standard container.
- Nullable reference types on; analyzers at `AnalysisMode=All` plus SecurityCodeScan and Roslynator (`backend/Directory.Build.props`, versions pinned; Roslynator only has `RCS1112` and `RCS1186` as warnings, the rest of its catalog was measured and left off, reasons in `backend/.editorconfig`; F4-0101); warnings are errors. Do not suppress rules to pass. `dotnet format --verify-no-changes` also reports analyzer errors (it caught `RCS1139`): run it, not only the build.

## Data and tenant isolation (ADR-002)
- Migrations: plain SQL files in `backend/migrations`, named `NNNN_name.sql`, applied in name order, one transaction per file, by `MigrationRunner.ApplyAsync(ownerConnectionString, dir)` with the OWNER credential (needs CREATEROLE). Never edit an applied file; add a new one (the runner stores a SHA-256 per file and throws if an applied file changed). The app credential never runs migrations.
- Two credentials: owner/migration (owns tables) and `flow4tech_app` (created NOLOGIN by migration 0001; the migrator gives it LOGIN + the `APP_DB_PASSWORD` value on deploy, idempotent, never from the repo; not owner, no BYPASSRLS, no DDL). The running app and all integration tests use the app credential.
- Writing a tenant table (copy `amostra_itens` in `0001_isolamento_base.sql`): `organizacao_id uuid NOT NULL REFERENCES organizacoes(id)`; `ENABLE` and `FORCE ROW LEVEL SECURITY`; policy `USING` and `WITH CHECK` on `organizacao_id = (SELECT app_organizacao_id())`; child references use composite FKs `(organizacao_id, parent_id) -> parent(organizacao_id, id)` (parent needs `UNIQUE (organizacao_id, id)`). The app role gets DML through default privileges; do not grant more. Only exceptions: `organizacoes` (tenant key is `id`) and `schema_migrations`, listed in `RlsArchitectureIntegrationTests`.
- Context API: all tenant data access goes through `TenantDatabase.BeginAsync(OrganizationContext)` (Infrastructure.Data), which opens a transaction and runs `set_config('app.organizacao_id', id, true)` (SET LOCAL semantics: dies with the transaction, never per connection). Use `tx.Connection`/`tx.Transaction`, call `CommitAsync`. Background jobs and event handlers open their own `BeginAsync` with the job's/event's organization. No context means zero rows and refused writes. Never build a connection that skips it.
- `FORCE` also binds the owner: seeds/backfills run inside a tenant context.
- `RlsArchitectureIntegrationTests` migrates a real database and fails the build for any table without the tenant column, enabled+forced RLS, or a policy on `app_organizacao_id()`. Adding a table needs no test edit. The accepted policy shape is exactly one policy FOR ALL TO PUBLIC with USING and WITH CHECK equal to the isolation expression; extra or different policies fail.
- Data-access style is EF Core with SQL kept visible and testable (ADR-002). (a) Every tenant query runs inside `TenantDatabase.BeginAsync`; a `DbContext` is never used outside it. Tenant contexts derive from `TenantDbContext` (Data project), which can only be constructed from the `TenantTransaction` (`public MyContext(TenantTransaction tx) : base(tx)`); build one per unit of work inside `await using var tx = await tenant.BeginAsync(ctx)`, commit with `tx.CommitAsync()`. Commands outside a live tenant transaction throw `TenantContextRequiredException`. Never `AddDbContext`, `AddDbContextFactory`, `UseNpgsql`, `DbContextOptions`, `: DbContext` (any spelling) or the literal `app.organizacao_id` outside Data (known limit: `tx.Connection` is public, so only the architecture ban and review stop hand-written `set_config`); no pooled or long-lived contexts.
- Schema is owned by SQL migrations, not EF: no EF migrations (Design/Tools packages banned), no `EnsureCreated`. RLS policies, `FORCE`, roles, composite FKs are in `backend/migrations`. Every module context needs an integration test with `Assert.Empty(await SchemaDrift.FindAsync(context))` (model vs migrated database).
- SQL stays visible: reads use `AsNoTracking()`; critical queries get a test asserting `ToQueryString()` text (see `TenantDbContextIntegrationTests`) and never filter on `organizacao_id` in the application (RLS does it). Raw SQL for hot or complex queries only as interpolated `FromSql($"...")`, `Database.ExecuteSqlAsync($"...")`, `Database.SqlQuery<T>($"...")` on the tenant context; `FromSqlRaw`/`ExecuteSqlRaw`/`SqlQueryRaw` are banned; never concatenate. Warm the EF model at host start (first query costs about 1 s).
- Enforced by `tests/Architecture` (`ModuleGraph.CheckTenantDataAccess`): `Npgsql` only in `src/Infrastructure/Data` (exemption: the readiness probe in `src/Api`); EF Core only in Data and module Infrastructure layers; Dapper and EF Design/Tools banned; only a module Infrastructure layer may reference the Data project. Get connections only from `TenantDatabase`.
- `backend/spikes/**` is disposable (Dapper vs EF evidence, Wolverine/Hangfire/Quartz comparison), outside `Flow4Tech.sln` (no CI gate builds it); never reference it from `src`.
- Background work and events (ADR-003): there is no ambient organization. A job carries `Job.Organization`; the handler restores it with `TenantDatabase.BeginAsync(job.Organization)` before touching data. Publish a domain event with `OutboxWriter.AddAsync(tx, organization, event)` on the SAME `TenantTransaction` as the state change (never its own transaction). `OutboxDispatcher.DispatchAsync(organization)` delivers at least once, running consumers inside a `BeginAsync` for the event's organization; consumers must be idempotent on `OutboxMessage.Id` (`IdempotentConsumer` + inbox table does it for database effects), and must not assume ordering. Queue/worker libraries only ever sit behind `IBackgroundJobs` (Quartz chosen; Wolverine and Hangfire compared in ADR-003). Name event types stably (`amostra.item-criado`); never rename one once published.
- Authorization (ADR-006): see "Authorization: asking Decidir" below.
- Organizations with pending events (ADR-003, ticket 07, migration 0011): table `outbox_organizacoes_pendentes` (ids and instant only; no RLS, NO privilege for `flow4tech_app`, listed as exempt in `RlsArchitectureIntegrationTests`), filled by a trigger on `outbox_eventos` in the event's own transaction (never insert into it by hand), read by `PendingOrganizationsDatabase` (Data) through the SECURITY DEFINER function `outbox_organizacoes_pendentes(limit)` (refuses to run inside a context) and closed per organization by `outbox_encerrar_pendencia()`. `OutboxSweeper.SweepAsync()` = list, `DispatchAsync` each organization under its own context, close. No BYPASSRLS role. A new SECURITY DEFINER function goes in the exact-set test in `IdentidadeSchemaIntegrationTests`. The sweep is not scheduled yet (needs the Quartz worker).

## Authorization: asking Decidir (ADR-006)
- One door: `IAuthorizationEngine.DecidirAsync(Subject who, string permission, Scope where, DecisionContext context, ct)` (`Flow4Tech.Kernel.Authorization`). Permission is `resource:action` from the catalog (`PolicySet.KnownPermissions`); unknown permission, no matching rule, no organization all deny. Precedence: explicit deny > allow > default deny. Callers and tests depend only on the interface (the engine is swappable: rules-as-data today in `Permissoes.Application`, `RulesAuthorizationEngine`); never evaluate profiles/roles yourself and never branch on a profile name.
- Unit of work (ADR-006 decision C, built): run the whole business operation inside `IUnitOfWork.ExecuteAsync(org, async ct => { ... })` (`Flow4Tech.Kernel`, implemented by `TenantUnitOfWork` in Data). It opens ONE tenant transaction: `DecidirAsync` (the cap reservation), the state change and `OutboxWriter.AddAsync` share it; it commits when the lambda returns and rolls back everything, reservation included, if it throws. Infrastructure code (repositories, outbox) gets the transaction from `TenantUnitOfWork.Require(organizationId)`; there is no other way to reach it, and `PostgresCumulativeLimitStore` throws outside a unit of work (a capped decision without one is a bug, not a silent separate transaction). Nested `ExecuteAsync` for the same organization joins; another organization throws. A business failure expressed as a return value does not roll back: throw. Kernel types never name a database type (guarded by `KernelContractTests`). Limits: no parallel work inside one unit of work (single connection); a nested scope that threw makes the outer unit roll back and throw even if the exception was swallowed; a scope is closed when it ends and `Require` throws on a closed scope (no fire-and-forget work using it); the counter row lock is held until the whole operation commits, so same-user capped operations serialize and counters taken in opposite orders can deadlock: keep units short.
- Ask in the Application handler, after loading the real operation and BEFORE any change: build `Scope` from the session (`OrganizationContext`; `UnitId` of the object being touched) and `DecisionContext` from server-side facts (`Value` = the computed total, `Percent` = from the stored order; there is no time field: the cap day is the unit's operating day from `IOperatingDayResolver`, so always pass `Scope.UnitId`). Never feed it numbers taken from the request body. A limited permission without the measured value is denied (fails closed), a capped request without `Scope.UnitId` is denied (`unit-required`), and limits are BRL only: any other currency is denied (`currency-not-supported`).
- `Decision.IsAllowed` false means stop and return 403 (do not leak why; log `Decision.Reason`). An Allow on a capped permission (cumulative daily limit) has reserved the budget atomically (one upsert in `PostgresCumulativeLimitStore`, RLS) INSIDE the caller's unit of work (see Unit of work above): do the work in the same `IUnitOfWork.ExecuteAsync`, and if it throws the reservation rolls back with everything else (ADR-006).
- ASP.NET: resource-based authorization. A `PermissionHandler : AuthorizationHandler<PermissionRequirement, OperationFacts>` maps the user's claims to `Subject` and calls `DecidirAsync` (working sample in `backend/spikes/authz/AspNetIntegrationTests.cs`). A name-only `[Authorize(Policy=..)]` never sees the values, so it cannot enforce limits: use it only for coarse "is signed in" gates, not for permissions with limits or unit scope.
- Test a new permission: add it to the catalog and to the profile x permission matrix in `AuthorizationEngineContract` (a test fails if a profile x catalog pair is missing), then run `dotnet test backend/tests/Authorization/Flow4Tech.Authorization.Tests.csproj`. A new engine implementation subclasses `AuthorizationEngineContract` and must pass it unchanged.
- Cumulative counters live in `limites_consumo` (migration 0003, key organization+user+permission+OPERATING day, RLS). The day is the unit's operating day, not UTC: `IOperatingDayResolver` (default `ConfiguredOperatingDayResolver`: unit time zone, default `America/Sao_Paulo`, rollover 05:00, from `IClock`; per-unit rules not persisted yet, roadmap 2.10b; the OPTIONS `dia-operacional.fuso|virada` exist in the layered settings since ticket 10, but this resolver does NOT read them yet). Limits are BRL cents only; any other currency denies. The reservation joins the business transaction through `IUnitOfWork` (ADR-006). Never read-then-write a counter in application code: the concurrency test (`Harness_detects_a_counter_without_locking`) shows that overshoots.

## Request context (plataforma base, ticket 01)
- Organization and unit come ONLY from the authenticated session. A route marked `.RequireSession()` goes through `RequestContextMiddleware` (Api), the single place that builds `OrganizationContext`: no valid session -> 401; a session that must still change its temporary password -> 403 (except routes marked `allowPasswordChangePending`); a session with no active unit -> 403 (except routes marked `allowWithoutUnit`: `GET /unidades`, `POST /sessao/unidade-ativa`, `POST /sessao/trocar-senha`, whose context then carries `Guid.Empty` as unit); no link in `usuario_unidades` (migration 0004, tenant table) to the active unit -> 403 without reason. Handlers take `IRequestContext` (Kernel) and run `IUnitOfWork.ExecuteAsync(request, ...)`; Application/Domain/Interface never write `new OrganizationContext(` (architecture test).
- `ClientContextInput` + `ClientContextInputTests`: no route may take `organizacaoId`/`unidadeId` (or synonyms) from route, query, header or body. A destination the user chooses (switch unit: `unidadeDestinoId`) is validated against their links, never trusted as context.
- Session seam: `ISessionSource` (Api) has ONE implementation, `BearerSessionSource` (ticket 04, see "Sessões e tokens"). ## Auditoria (plataforma base, ticket 02, spec 5.6)
- Write: inject `IAuditLog` (Kernel) in an Application handler and call `audit.RecordAsync(request, new AuditEntry { Action = <catalog const>, Result, ObjectType, ObjectId, Before, After }, ct)` INSIDE the action's `IUnitOfWork.ExecuteAsync` (user, session and unit come from `IRequestContext`). Same transaction: if the action throws, the record is rolled back with it; outside a unit of work it throws. Add the audit step to every state-changing ([A]) action; `UnidadesDoUsuario.TrocarAsync` is the model.
- Deliberate failures (login denied, access denied) use `RecordDetachedAsync`: its own transaction, persists even though the operation failed; call it AFTER the unit of work ended (it throws inside one: both would contend for the chain lock). Result is `Sucesso`, `Negado` or `Falha`.
- Action names: `recurso:acao` constants in a static class marked `[AuditCatalog]` (Kernel `PlatformAuditActions` for the platform; each module declares its own). Never a string literal (architecture test), never renamed once published: `backend/audit.catalog.txt` is append-only (`UPDATE_AUDIT_CATALOG=1 dotnet test backend/tests/Architecture/Flow4Tech.Architecture.Tests.csproj` adds new names; a removed or renamed name fails the build).
- Table `auditoria_registros` (migration 0005): tenant table with the exact RLS policy; append-only by PRIVILEGE (`flow4tech_app` has SELECT and INSERT only: UPDATE/DELETE/TRUNCATE fail with 42501). Never edit it as the app credential; there is no "fix a record" path, a correction is a new record. The chain per organization: `sequencia` (1,2,3...) and `hash_anterior`/`hash` = SHA-256 of a canonical JSON form (`AuditHash`, canonicalization version `v:1`: fixed field order, sorted keys, numbers via decimal, instant at microseconds). Concurrent writers of one organization serialize on a transaction advisory lock keyed by the organization; `UNIQUE (organizacao_id, sequencia)` is the backstop. Keep units that audit short (the lock is held until commit).
- Verify: `AuditChainVerifier.VerifyAsync(organization, anchor?)` reports `Altered`, `Removed`, `Reordered`, `Truncated` and raises the outbox event `auditoria.integridade-violada` (no consumer yet). Job: `AuditJobs.VerifyChain(org)` + `AuditJobs.Handler(verifier)` behind `IBackgroundJobs`; the recurring trigger is NOT scheduled yet. One outbox event per DISTINCT violation (state in table `auditoria_verificacao`, migration 0006: the alerted violation set; cleared when the chain verifies valid again, so a new break alerts again). The head of every VALID run is stored there as the anchor of the next run, so the job (which passes no anchor) detects a removed tail; an explicit `anchor` overrides the stored one. That table is tenant + exact RLS but the app credential can INSERT/UPDATE it (not DELETE/TRUNCATE); `auditoria_registros` stays append-only. Limits: the first run of an organization has no anchor; the stored anchor lives in the same database, so whoever can also rewrite that row (the OWNER credential) defeats it; rewriting the whole table with recomputed hashes needs the off-database copy (spec debt, open question 3).
- Secrets: `SensitiveData` is the one rule. Keys that contain senha, password, passwd, pwd, passcode, token, secret, segredo, credencial, credential, apikey, accesskey, authorization, cookie, hash, bearer, privatekey (case, `_` and `-` ignored), keys that have `pass`, `pin`, `otp` or `jwt` as a WHOLE word (`userPin`, `sms-otp`, `PIN_CODE`; not inside `shipping`/`passageiro`; a one-run lower-case `userpin` is not caught), keys that themselves look like a secret, and values that look like a JWT, bcrypt/argon2/PBKDF2/Identity hash or `Bearer`/`Basic` credential. In `Before`/`After`/object reference the audit REJECTS (`AuditSecretException` with the JSON path, never the value; nothing is stored). A number outside the range of `decimal` is refused the same way with `AuditValueException` (path only, nothing stored); the technical log MASKS (`***`). Over-strict on purpose (a field named `hash` is refused): rename it.
- Technical log: `ITechnicalLog.Write(severity, "evento.nome", fields)` (separate from the audit, JSON console with scopes). The correlation id is the W3C trace id (`traceparent`, `Correlation.Current`): `CorrelationMiddleware` returns it as `X-Correlation-Id`, writes the `http.requisicao` line (method, route pattern, status only; the framework's request line is muted because it prints the query string) and every audit record stores it. Never log a request body, header, cookie or query value.

## Sessões e tokens (plataforma base, ticket 04, spec 5.3, ADR-010)
- Module: sessions live in `Identidade` (`Sessoes` in Application; `JwtEmissorDeTokens`, `PostgresSessaoStore`, `OutboxEventosDeSeguranca` in Infrastructure). Identidade stays independent: it learns the account's units through its own port `IUnidadesDaConta`, adapted in Api (`UnidadesDaContaAdapter`) over the Organizacao port.
- The session is a ROW (`sessoes`, migration 0009, tenant table, exact RLS, composite FKs to `contas`/`unidades`); the access token only names it. Per request `Sessoes.AutenticarAsync` checks signature/audience/exp (`IClock`), then the session row JOIN the account: not revoked, inside inactivity (default 12 h, slides, write at most once a minute) and absolute (default 14 days) limits, account active, `sessoes.versao_credencial = contas.versao_credencial = ver` of the token. So password change, deactivation, owner flag change, revoke, expiry take effect on the NEXT request; removing the user-unit link revokes the sessions working in that unit (trigger in 0009). A new permission/profile change (tickets 05/06) must bump `versao_credencial` or call `ISessaoStore.RevogarOutrasDaContaAsync`. Measured: ~4 ms p50 per check, no cache (ADR-010).
- Token: JWT HS256 (`Microsoft.IdentityModel.JsonWebTokens` 8.14.0), claims `sub`, `org`, `sid`, `ver`; audience = realm (`app`; `control` only reserved: its own key and audience, no route issues it); 5 min, 30 s skew; algorithm pinned, `none` refused. Keys ONLY from configuration: `Flow4Tech:Tokens:AppKey` (>= 32 bytes; rotate by moving it to `AppKeyPrevious`), `ControlKey`; the host does not start without `AppKey` outside Development/Testing (there a missing key makes an ephemeral one). Read from `Authorization: Bearer` only. Never write a key literal in code (`SessionDoorTests`).
- Refresh: opaque `r1.<org>.<256 bits>`, stored as SHA-256 only (`sessao_refresh`), rotated on every use; a used token presented again revokes the session, audits `sessao:refresh-reutilizado` and raises the outbox event `seguranca.refresh-reutilizado` (once per session). Two simultaneous refreshes with the same token: one wins, the other is a reuse and the session dies, so a client must refresh from a single place at a time. Cookie `__Host-f4t_refresh` (HttpOnly, Secure always, SameSite=Strict, Path=/), set by `RefreshCookie`. In plain-HTTP tests read `Set-Cookie`, assert, and replay it in a `Cookie` header.
- Routes: public `POST /login`, `POST /refresh`, `POST /logout` (allowlisted by method+pattern in `RoutePermissionTests.PublicWithoutSession`, each declares a `sessao:*` permission); `POST /sessao/trocar-senha`, `GET /sessoes`, `GET /sessoes/todas`, `POST /sessoes/{id}/revogar`. The three public routes carry `.RequireCsrfGuard()` (header `X-F4T-Csrf: 1`, own-authority/configured `Origin`, `Sec-Fetch-Site`) and every body-reading route `.WithBodyLimit(n)` (`RouteGuardsMiddleware`, 413). Login body names the typed organization `organizacaoDoLogin` (not a context field). One failure for login (401, empty body, no cookie).
- States: login with a temporary credential gives a session that reaches only `POST /sessao/trocar-senha` and `POST /logout` (403 elsewhere); the change revokes every other session of the account and returns a new normal one. With one linked unit it becomes active at login; with several or none the session starts without one (only the selection routes work). Other people's sessions: owner only for now (`sessao:ver-todas`/`sessao:revogar` are declared; ticket 05 turns it into `DecidirAsync`).
- Audit actions (`IdentidadeAuditActions`): `sessao:iniciar`, `sessao:encerrar`, `sessao:revogar`, `sessao:refresh-reutilizado` (+ `sessao:trocar-unidade`). Audit data never carries a key containing "senha"/"token": use `restrita`, `motivo`.
- Config (env, defaults): `Flow4Tech__Sessoes__InatividadeHoras` (12), `AbsolutaDias` (14), `IntervaloDeAtividadeSegundos` (60), `AllowedOrigins__0..` (none), `Flow4Tech__Tokens__AccessMinutos` (5). The clocks are layered settings since ticket 10 (see "Configurações em camadas"): the variables above are their SYSTEM layer.

## Proteção de login e alertas (plataforma base, ticket 08, spec 5.5)
- `Autenticacao` judges every attempt BEFORE any lookup or hashing with `ILimitadorDeLogin` (Application port; `LimitadorDeLoginEmMemoria` in Infrastructure): progressive lock per account AND per address (`base * 2^(failures - limit)` up to a ceiling), different limits for e-mail and operational accounts, credential stuffing (many accounts from one address; many addresses against one account), adaptive CAPTCHA. Thresholds: `LimitesDeLogin`, built from the system layer of the `bloqueio.*` settings (`Flow4Tech:Identidade:Bloqueio:*`, ticket 10). The key is the TYPED identifier, never the account found, so unknown names lock exactly like known ones; a blocked attempt does no hashing, is not audited, still waits the response-time floor, and answers `LoginBloqueado` (`POST /login` 429 + `Retry-After`) or `CaptchaExigido` (428). Overloads with `ContextoDeLogin(ip, captchaResposta)`; the ones without it count by account only.
- State is IN PROCESS memory (lost on restart, per instance, bounded at `MaximoDeRegistros`). Shared/general rate limiting is deliberately postponed (F4-0096, ADR-011 "Decision update"): it becomes mandatory before running a second API instance. Swapping it for a shared store means changing the port. An address has no organization: its lock goes to the technical log (`login.ip-bloqueado`, address only as an 8-hex digest). The address comes from `RemoteIpAddress`; behind Railway set `Flow4Tech__Rede__ProxyConfiavel=true` (last `X-Forwarded-For` entry, `ForwardLimit=1`; only safe if the API is reachable through the proxy alone).
- CAPTCHA: `ICaptcha` has no provider (`CaptchaNaoConfigurado`, `Configurado=false` = never asked). E-mail: `IEnviadorDeEmail`; `EnviadorDeEmailDeDesenvolvimento` keeps messages in memory and logs the subject only (never recipient or body). No e-mail really leaves until the provider (open question 4).
- Security events (outbox, same unit of work as the action): `seguranca.login-novo` (`Sessoes.CriarAsync` via `IAcessosConhecidos`: device = user agent without digits, place = network prefix IPv4 /24 / IPv6 /64, table `acessos_conhecidos`, migration 0012, max 50 per account and kind; the first login of an account only sets the baseline), `seguranca.conta-bloqueada` (+ audit `autenticacao:bloquear`, known accounts only), `seguranca.senha-trocada`, and the older `seguranca.refresh-reutilizado`. `AlertasDeSeguranca.Consumidores` turns the first three into e-mails to the person (if the account has an e-mail) and to the active owners; registered as `IOutboxConsumer` (idempotent on the event id). The dispatcher is still not in the DI nor scheduled, so nothing runs them in production yet.
- Tests: `LimitadorDeLoginTests`, `AutenticacaoProtegidaTests`, `ImpressaoDeAcessoTests` (no database); `AlertasDeSegurancaIntegrationTests` (PostgreSQL); `SessoesEndpointsTests.Repeated_failures_lock_...` (HTTP). Recovery without enumeration reuses the limiter (done in ticket 09, see below).

## Convites, recuperação e Google (plataforma base, ticket 09, spec 5.2.1, 5.2.3, 5.2.5, 5.2.6)
- Tokens de uso único (`TokenDeUso`): convite `c1.<org 32 hex>.<256 bits>`, recuperação `a1.<...>`; só o SHA-256 do texto inteiro é guardado (`convites`, `recuperacoes`, migração 0013, tenant, RLS exata). NUNCA cria conta; vínculo só pela pessoa logada com senha atual, e-mail do Google verificado e igual ao da conta (`identidades_externas`, FK composta com o tipo `email`: o banco recusa conta operacional; `UNIQUE (provedor, sub)`); entrar exige o `sub` vinculado; todo o resto é `GoogleNeutro`. ## Configurações em camadas (plataforma base, ticket 10, spec 5.7)
- Declare an option in code: a `public static readonly SettingDefinition` in a static class marked `[SettingsCatalog]` (Kernel `Flow4Tech.Kernel.Settings`: key `grupo.nome`, type `Inteiro|Numero|Booleano|Texto|Hora`, default, `SettingLayers` = `SomenteSistema|Organizacao|OrganizacaoEUnidade`, optional `Minimum/Maximum/Validator`, `ConfigPath`, `RequiresEffectiveInstant`). Collected from the module assemblies (`ModuleCatalog.LoadSettings`), validated at start (`SettingsCatalog`), exported to `backend/settings.catalog.txt` (`UPDATE_SETTINGS_CATALOG=1 dotnet test backend/tests/Architecture/...`; a published key is never removed or renamed). Declared today: `IdentidadeSettings` (`sessao.*`, `bloqueio.*`) and `OrganizacaoSettings` (`dia-operacional.fuso|virada`).
- Resolution: system > organization > unit (`ResolvedorDeConfiguracao`, pure). The SYSTEM layer is the declared default overridden by configuration (`SystemConfigPath` = `ConfigPath` or `Flow4Tech:Configuracoes:<key>`; the old `Flow4Tech:Sessoes:*` and `Flow4Tech:Identidade:Bloqueio:*` keep working this way; an invalid configured value stops the host, it is never replaced by the default). The organization may LOCK an option (`travado`): the unit value is then inert. A unit layer needs the organization layer. Other modules read through `ISettings` (Kernel): `SystemValue(def)` (sync, no database) or `ResolveAsync(def, org, unit, at, ct)`; the instant is explicit, so reading a past instant keeps reading what applied then. Without the host's real `ISettings` (tests), `AddIdentidade` registers a system-only one fed by `IdentidadeOptions`.
- Storage: `configuracoes_versoes` (migration 0014, tenant table, exact RLS, APPEND-ONLY by privilege like the audit trail). One row = one version of an option at one scope (organization when `unidade_id IS NULL`, or one unit); `valor` NULL = inherit; `vigente_a_partir_de >= criado_em` is a CHECK (a change never reaches back). Effective version at an instant = the highest version number among those already started, so a version written later cancels one scheduled that has not started. Restore = a new version that copies an old one (`restaura_versao`). Writers of the same scope and key serialize on an advisory lock (`ProximaVersaoAsync`).
- Change only through `Configuracoes` (Organizacao.Application): `AlterarAsync`, `RestaurarAsync`, `HistoricoAsync`, `ListarAsync`. One unit of work each: asks `IPermissaoDoChamador` (adapted in Api over the one engine) for `organizacao:configurar`, validates layer/value/lock/instant, appends, audits (`configuracao:alterar|restaurar` with before/after). The unit layer is the session's ACTIVE unit (never named by the client); an option with `RequiresEffectiveInstant` must name the instant; an instant before now is refused. Routes (all `organizacao:configurar`; the two writes are `sensitive`): `GET /configuracoes`, `PUT /configuracoes/{chave}`, `GET /configuracoes/{chave}/historico?camada=`, `POST /configuracoes/{chave}/restaurar`.
- Consumers: `Sessoes` reads the two clocks per organization (`ConfiguracoesDeIdentidade.RelogiosAsync`: at session start, and the inactivity window whenever a session slides; `sessao.intervalo-atividade-segundos` is system-only so the per-request path pays no read); the absolute limit is fixed when the session starts, so a change reaches only sessions that start after it. The login lock policy (`bloqueio.*`) is SYSTEM ONLY on purpose (the limiter judges before any lookup; an address has no organization). The operating-day resolver still reads its own default (roadmap 2.10b).
- Limits: no profile layer (spec 5.3.4 mentions "por perfil"); no cache (one extra read when a session slides its window, once per interval per session); `temp credential`/`invite`/`recovery` durations are still options on `IdentidadeOptions`, not settings.

## Permissions on HTTP (plataforma base, ticket 05, spec 5.4)
- `.RequirePermission(X)` is now DECIDED, not only declared. `PermissionMiddleware` (after `RequestContextMiddleware`, which answers 401) calls `IAuthorizationService` -> `PermissionHandler : AuthorizationHandler<PermissionRequirement, OperationFacts>` -> `IAuthorizationEngine.DecidirAsync` with `Subject(user, profiles)` and `Scope(organization, active unit)`. Denied: 403 with an EMPTY body; the engine's reason goes only to the technical log (`acesso.negado`: permissao, motivo, usuarioId, sessaoId). Route-level decisions carry no operation values, so a permission with a limit is asked in the Application handler, not here.
- A route that declares a permission must also be `.RequireSession()`, unless it is in `RoutePermissions.PublicWithoutSession` (`GET /version`, `POST /login|/refresh|/logout`). The host refuses to start otherwise (`RoutePermissions.EnsureValid` -> `CheckSessions`), and so does the architecture test.
- Audit of denials: opt in with `.RequirePermission(X, sensitive: true)` (e.g. `GET /sessoes/todas`). A denial there writes `acesso:negar` (result `negado`, object = the permission, no reason) with `RecordDetachedAsync`; every audited denial takes the organization's chain lock, so do not mark routes sensitive by default. If the audit store is down the request fails (500), it is never swallowed.
- Profiles: `IPerfisDoUsuario.ListarAsync(organization, userId)` (Permissoes.Application) lists the profile KEYS of a person; the host adapter `PerfisDaConta` gives the factory key (owner `dono`, other active account `conta`, inactive none), the custom profiles assigned to the person and their private override key (see "Perfis persistidos"). The rules are `PoliticaDeFabrica` (`PolicySet` data, built from the catalog by `AddPermissoes(catalog)`); a permission it grants that the catalog lacks stops the host. `conta` gets only what concerns itself (`organizacao:ver-unidades`, `organizacao:trocar-unidade`, `sessao:trocar-senha`, `sessao:ver-proprias`, `sessao:revogar-propria`, `conta:gerir-google`); `dono` gets the whole catalog. `POST /sessoes/{id}/revogar` declares `sessao:revogar-propria`; the SERVICE still lets only an owner end someone else's session (`sessao:revogar` is not asked of the engine yet).
- No code branches on a profile name (`ProfileBranchingTests`): only `PoliticaDeFabrica.cs` and `Api/PerfisDaConta.cs` may name a factory profile, only `PolicyEvaluator` reads `Subject.Profiles`, and no source compares a profile to a value.
- Contract: every operation with a declared permission carries `x-permission` in `openapi.json` (an operation transformer in `Program.cs`); `RoutePermissionTests` checks the committed document against the declared routes. The generated TypeScript client is regenerated with the document (`pnpm --filter @flow4tech/api-client generate`); the `openapi-contract` gate fails on any difference.

## Perfis persistidos (plataforma base, ticket 06, spec 5.4.3 a 5.4.9)
- Factory profiles (`dono`, `conta`) stay code (`PoliticaDeFabrica`), not editable, only duplicable. Custom profiles, their rules, assignments and individual overrides are tenant tables of migration 0010 (`perfis`, `perfil_regras`, `usuario_perfis`, `usuario_regras`). A custom profile's key for the engine is its id (`ChavesDePerfil.Personalizado`); a person's overrides are one more private profile `usuario:<id>` (`ChavesDePerfil.DoUsuario`), so the engine has no special case.
- The engine reads rules through `IPolicySource`: `PostgresPolicySource` = factory rules + the organization's persisted rules, per decision, no cache (a change is in force on the next decision). It joins the unit of work in progress or opens a short read transaction. Tests with a fixed policy use `new RulesAuthorizationEngine(policySet, ...)` (a `StaticPolicySource`).
- Manage only through `GestaoDePerfis` (`CriarAsync`, `DuplicarAsync` copy or follow, `SubstituirRegrasAsync`, `AtribuirAsync`, `RemoverAtribuicaoAsync`, `DefinirOverridesAsync`): one unit of work each; asks the engine for `perfil:gerir` / `permissao:atribuir`; nobody changes their own rights (own assignment, own override, a profile they hold) -> `AutoPromocao`; nobody hands on what they do not hold or hold less generously (`GrantGuard`) -> `EscalacaoNegada`. Both are audited as `permissao:negar-escalada` (negado, detached). Results are `ResultadoGestao`, the route maps them (403 without reason for `Negado`/`AutoPromocao`/`EscalacaoNegada`).
- Every change of rights bumps `contas.versao_credencial` of the affected accounts by database triggers (migration 0010), which ends their sessions on the next request (5.4.9). A change to the factory rules in CODE does not.
- Simulator: `SimuladorDePermissoes.SimularAsync` asks `DecidirAsync` for another person inside a unit of work that is rolled back, so it never reserves a cap. Needs `perfil:ver` or `permissao:atribuir`. Never call it inside another unit of work.
- Gotcha: `ProfileBranchingTests` is a regex; do not name an identifier `Perfil*`/`Profile*` right before `==`/`!=` or call `.Equals` on it (EF properties are `IdDoPerfil` for that reason).
- A rule scoped to a unit must name a unit of the SAME organization (`GestaoDePerfis.UnitsExistAsync`; unknown or foreign unit = `Invalido`, never a foreign-key 500).
- Tests: `PerfisPersistidosIntegrationTests` (behaviour), `PersistedRulesEngineTests` (the whole engine contract over rules read from the database), `CumulativeLimitFromPersistedRulesIntegrationTests`, `GrantGuardTests`. No HTTP routes manage profiles yet (pending: `perfil:gerir`, `perfil:ver`, `permissao:atribuir` are in the catalog and no route asks for them).

## A rota autenticada de ponta a ponta (fechamento da 1A)
Ordem de uma requisição a uma rota de negócio, com quem decide cada passo (os middlewares estão em `Program.cs`, nesta ordem):
1. `CorrelationMiddleware`: id de correlação = `traceparent` W3C, devolvido em `X-Correlation-Id`; linha `http.requisicao` (método, padrão da rota, status) no log técnico. Atrás do Railway, `UseForwardedHeaders` só com `Flow4Tech__Rede__ProxyConfiavel`.
2. `RouteGuardsMiddleware`: limite de corpo (`.WithBodyLimit(n)`, 413) e guarda de CSRF das rotas públicas com cookie (`.RequireCsrfGuard()`).
3. `RequestContextMiddleware` (único lugar que monta `OrganizationContext`): rota sem `.RequireSession()` passa; com ela, `BearerSessionSource` -> `Sessoes.AutenticarAsync` (assinatura, audiência `app`, `exp`; depois a linha da sessão JOIN a conta: não revogada, dentro dos dois relógios, conta ativa, `versao_credencial` igual). Sem sessão válida: 401. Sessão que deve trocar a senha: 403 (menos `allowPasswordChangePending`). Sem unidade ativa: 403 (menos `allowWithoutUnit`). Sem vínculo em `usuario_unidades` com a unidade ativa: 403 sem motivo. Organização e unidade vêm SÓ daqui, nunca do cliente (`ClientContextInputTests`).
4. `PermissionMiddleware`: `.RequirePermission(X)` -> `IAuthorizationService` -> `PermissionHandler` -> `IAuthorizationEngine.DecidirAsync(Subject(usuário, perfis de IPerfisDoUsuario), X, Scope(organização, unidade ativa))`. Negado: 403 de corpo vazio, motivo só no log (`acesso.negado`); com `sensitive: true` também `acesso:negar` na auditoria. Regras de fábrica (código) + regras da organização lidas do banco a cada decisão (ADR-006).
5. Handler da rota: recebe `RequestContextAccessor`/`IRequestContext`, valida a entrada no Interface e chama um serviço de Application.
6. Serviço de Application: `IUnitOfWork.ExecuteAsync(request, ...)` abre UMA transação de tenant (`set_config('app.organizacao_id', ..., true)`); dentro dela, nesta ordem: carregar o objeto real, `DecidirAsync` com os valores do servidor (teto/limite reservam atomicamente), a mudança de estado, `IAuditLog.RecordAsync` (mesma transação, cadeia por hash) e `OutboxWriter.AddAsync` (evento de domínio/segurança). Erro de negócio = lançar (desfaz tudo). Falha deliberada (negado) = `RecordDetachedAsync` DEPOIS da unidade.
7. Banco: RLS forçada com a credencial `flow4tech_app` filtra tudo pela organização do passo 6; sem contexto, zero linhas e escrita recusada. Nada no código filtra por `organizacao_id`.
8. Depois do commit: o despachante entrega o outbox (e-mails de alerta, etc.). O varredor e o agendamento ainda NÃO estão ligados (precisa do worker Quartz).
Antes da sessão (sem organização): login, refresh, logout, convite aceito, recuperação e Google são rotas públicas (`RoutePermissions.PublicWithoutSession`); só `PreAuthDatabase` + 3 funções `SECURITY DEFINER` (ADR-005) e tokens com a organização como localizador (ADR-012) rodam sem contexto. Limite de tentativas: ADR-011.
Prova: `DoisTenantsEndpointsTests` faz login real em duas organizações e confere unidades, sessões, configurações, perfis, convites, contas e auditoria, mais uma varredura de todas as tabelas com `organizacao_id` (linha de outra organização = 0; sem contexto = 0). Pendências conhecidas da 1A estão em `.scratch/S-02-plataforma-base/state.md`.

## Branches, IDs e PRs (ADR-016) — obrigatório para todo agente
- **Todo trabalho tem um ID de ticket `F4-NNNN`** (sequencial, único, nunca reaproveitado), registrado em `docs/tickets.md` ANTES de começar: acrescente a linha com o próximo número livre (título, fatia, spec, arquivo do ticket). Sem ID não há branch, commit nem PR. Manutenção também abre ticket.
- **Branches de longa vida do sistema novo:** `main-v2` (revisado, publicável) e `dev-v2` (integração). `main-v2` nunca recebe commit nem push direto, só PR vindo de `dev-v2`. `dev-v2` aceita commit e push direto (o ID `F4-NNNN` continua obrigatório no commit); branch de ticket + PR segue valendo para trabalho maior ou quando o dono pedir. `main`, `staging`, `development` e `refactor-v2` são o sistema antigo e o planejamento: não tocar.
- **Branch de trabalho:** `<tipo>/F4-NNNN-<resumo-em-kebab>`, criada a partir de `dev-v2`; tipos `feat|fix|refactor|test|docs|chore`; exemplo `feat/F4-0013-fila-offline`. Uma branch por ticket, vida curta. Se o ambiente impuser outro nome de branch (sessão de nuvem `claude/...`), use-o, mas o ID continua obrigatório nos commits e no PR.
- **Commit:** Conventional Commits em inglês com o ID como escopo: `feat(F4-0013): offline pending-actions queue`. Corpo curto dizendo o que foi provado. Nunca reescrever commits já publicados.
- **PR:** só quando o dono pedir. Título igual ao commit principal (`feat(F4-0013): ...`), alvo `dev-v2` (de `dev-v2` para `main-v2` só em entrega revisada), corpo pelo template `.github/pull_request_template.md` com o ID. Merge de feature em `dev-v2` por squash; `dev-v2` -> `main-v2` por merge commit.
- **Toda fatia tem ID `S-NN`** (sequencial, único, nunca reaproveitado; `S-00` a `S-04` já existem). A pasta é `.scratch/S-NN-<nome>/` e o prefixo ordena as fatias por data de criação. Registre a fatia na tabela "Fatias" de `docs/tickets.md` (ID, nome, abertura, fechamento, tickets) ANTES de criar a pasta; a coluna Fatia do índice usa o nome completo (`S-02-plataforma-base`). O `spec.md` começa com `Fatia: S-NN`, `Aberta: AAAA-MM-DD`, `Fechada: AAAA-MM-DD` (ou `em andamento`) e `Tickets: F4-NNNN..F4-NNNN`. Nunca renomeie uma fatia publicada. Trabalho transversal (manutenção, CI, docs de processo) não é fatia: usa a fatia `governanca`, trilho permanente sem `S-NN` em `.scratch/governanca/` (texto de PR em `pr/F4-NNNN.md`, notas); o ID `F4-NNNN` vale como em qualquer ticket.
- **Fechar o ticket:** `**Status:** done` no arquivo do ticket e a linha em `docs/tickets.md` com branch, PR e status atualizados. Os 38 tickets anteriores são `F4-0001` a `F4-0038` (mapeados no índice); commits antigos não são reescritos.
- **Rastrear:** `git log --grep "F4-0013"`, busca de PR por `F4-0013`, `git branch -a | grep F4-0013`, e o índice.
- **Hooks locais (Husky, `.husky/`, instalados por `pnpm install` na raiz):** `pre-commit` bloqueia commit direto em `main-v2`, `main`, `staging`, `development` e `refactor-v2`, roda `dotnet format` nos `.cs` em staging recusa marcador de conflito e roda `gitleaks git --pre-commit --staged` (aviso, sem bloquear, se o binário não estiver instalado: `brew install gitleaks`; F4-0088); `commit-msg` exige `tipo(F4-NNNN): descrição` (merge/revert/fixup passam); `pre-push` bloqueia push direto nessas branches e roda `dotnet build`, os testes de arquitetura e unitários (sem Docker), `pnpm -r typecheck` e `pnpm -r --if-present test` (suíte completa com Docker: `PRE_PUSH_FULL=1 git push`). Não use `--no-verify`; o CI roda os mesmos gates. O front usa Biome (F4-0099): o `pre-commit` roda `biome check --staged --write` nos arquivos do front em staging (corrige formatação sozinho, bloqueia erro de lint, milissegundos); o `pre-push` roda `pnpm lint` na árvore inteira antes do typecheck e dos testes; o CI roda o mesmo (`lint-frontend`). Sem eslint nem prettier.

## Writing a route the secure way
1. Resolve the organization/unit from `OrganizationContext` (authenticated session), never from client input.
2. Declare `.RequirePermission(...)` on the route and authorize explicitly with a named permission before any work; deny by default.
3. Validate input at the Interface layer; pass typed commands to Application.
4. Scope every query by organization (and unit when applicable).
5. Audit state-changing actions (`IAuditLog`, see "Auditoria"); return no data the caller's permission does not cover.
6. Cover the route with a test for the allowed case and for the denied/cross-organization case.
(Step 2 is `IAuthorizationEngine.DecidirAsync`, see above and "A rota autenticada de ponta a ponta". Keep this list in sync with that section.)
