# 006. Authorization: own rules-as-data engine behind a single decision interface (Cedar and Casbin measured, swappable)

- Status: accepted (spike ticket 09; owner decisions of 2026-11-02 recorded below)
- Date: 2026-11-02

## Context
Every route must ask one place whether `who` may do `resource:action` `where` given a `context` (03-seguranca S8: explicit deny > allow > default deny; limits judged on the REAL operation value, not what the client says). 04-arquitetura A14 left open whether to adopt Cedar, build, or mix. Three real cases decide it: (1) a waiter may give a discount up to X% by profile, above it is denied; (2) courtesies with a CUMULATIVE daily cap, where two concurrent requests must not jointly exceed it; (3) the same permission, a manager allowed only on unit 2 and denied on unit 1. Plus: explicit deny beats allow, default deny, unknown permission denies.

## Decision
1. **One interface, `IAuthorizationEngine.DecidirAsync(Subject who, string permission, Scope where, DecisionContext context)`** in `Flow4Tech.Kernel.Authorization`. Callers and tests depend only on it. A behavioural contract (`tests/Authorization/AuthorizationEngineContract.cs`: 56 tests including the profile x permission matrix) runs unchanged against every implementation.
2. **Build, do not adopt: the production engine is our own rules-as-data engine** (`Permissoes.Domain` pure `PolicyEvaluator` + `Permissoes.Application` `RulesAuthorizationEngine`). Rules are data (`Rule(effect, profile, permission, unit?, maxPercent?, maxValueCents?, dailyCapCents?)` over a catalog of known permissions). Cedar and Casbin.NET were adapted behind the same interface and pass the same contract, so choosing later is a swap, not a rewrite.
3. **Cumulative limits are owned by us in every option** (none of the three engines is stateful): the counter is a PostgreSQL tenant table (`limites_consumo`, migration 0003, RLS) updated by ONE atomic statement (`INSERT .. ON CONFLICT DO UPDATE .. WHERE total + amount <= cap`) run on the transaction of the caller's unit of work (`IUnitOfWork`, decision C), so it commits or rolls back with the business operation. This is the "hybrid" part and it is the same whichever engine decides the rest.
4. ASP.NET integration is resource-based authorization (`AuthorizationHandler<PermissionRequirement, OperationFacts>` that calls the interface). Name-only `[Authorize(Policy=..)]` cannot see operation values and is not used for permissions with limits.

Cumulative cap on PostgreSQL under RLS, app credential, through the interface (`CumulativeLimitConcurrencyIntegrationTests`): 40 concurrent requests of R$ 1,00 against a R$ 10,00 cap allow exactly 10 and persist exactly 1000 cents, on 3 consecutive fresh days (the "row does not exist yet" insert race included); 40 concurrent mixed amounts keep the persisted total equal to the sum of the allowed ones and within the cap; per-organization isolation holds with the same user id. The same tests go red when the counter is replaced by read-then-write without a lock (40 allowed instead of 10; 12 instead of 10 in the per-organization test; the mixed-amount test let 6980 cents through a R$ 10,00 cap while only 76 were persisted, lost updates), and a permanent test keeps that unlocked store as a test double to prove the harness can fail. Cost: a capped decision is one transaction, 1.8 ms sequential (mean, including opening the tenant transaction and an EF context), about 870-950 decisions/s with 40 pooled connections, also when all callers hit the same counter row.

## Why build
- Expressiveness for what we need is equal: all three express per-operation percent/value limits and unit scoping; none expresses the cumulative limit, so the decisive piece is ours regardless. Choosing Cedar buys a policy language, schema validation and formal analysis we do not use yet, at the price of a translation layer, a pre-1.0 single-vendor binding and about 1 ms per decision (about 1000x the own engine; fine for a screen, wasteful for list endpoints that filter many rows).
- The own engine is about 150 lines, pure (no I/O), trivial to test exhaustively, and the rules stay data we can persist per organization later.
- Because the interface and contract are fixed, the cost of being wrong is one adapter plus a data migration of the rules.

## Owner decisions (2026-11-02)
- **A. Cap day is the unit's OPERATING day, not the UTC date.** The counter key `dia` is the operating date: the local calendar date in the unit's time zone, shifted back by a per-unit rollover time (a moment before the rollover still belongs to the previous date). Defaults: zone `America/Sao_Paulo`, rollover `05:00` (after late closing, before the morning opening; a unit that closes later or opens earlier overrides it). The cap stays per user: the counter key is organization + user + permission + operating date, WITHOUT the unit (the unit only selects the zone/rollover), so a user working in two units with different rules shares one counter per operating date. Implementation: `OperatingDayRule` (Domain, pure; compares local wall-clock so DST never splits or merges a day) and the port `IOperatingDayResolver` (Permissoes.Application); `ConfiguredOperatingDayResolver` is the default, reading `IClock` plus an in-memory per-unit rule map (a capped request with no `Scope.UnitId` is DENIED with reason `unit-required`, nothing consumed: there is no honest day to count in). Per-unit settings are NOT persisted and have no UI yet: the future opening-hours feature (roadmap 2.10b) implements the port and feeds it the real hours. The runtime image needs tzdata (the aspnet Debian image has it); an unknown zone id fails when the rule is built.
- **B. Currency: BRL only.** Limits are integer cents of BRL. A value in any other currency (or an empty or lowercase code) is denied with reason `currency-not-supported` (distinct from `limit-exceeded`; covers cumulative caps and per-operation value limits, including `default(Money)`; consumes nothing). Permissions without value limits are unaffected.
- **C. Reserve-then-fail: decided and BUILT (ticket 10).** The reservation joins the SAME database transaction as the business operation through `IUnitOfWork` (Kernel, no database type in the contract) implemented by `TenantUnitOfWork` (Infrastructure.Data) over `TenantDatabase`: `ExecuteAsync(org, work)` opens one tenant transaction, exposes it as an ambient (AsyncLocal) to Infrastructure code via `TenantUnitOfWork.Require(organizationId)`, commits on return and rolls back on throw. `PostgresCumulativeLimitStore` no longer commits or opens its own transaction and throws outside a unit of work. A failed operation therefore rolls its reservation back and a retry cannot double count; the outbox event and the state change share the same transaction. Proved on real PostgreSQL under RLS in `UnitOfWorkIntegrationTests`, and the 40-concurrent cap test runs through the seam (`Harness_detects_a_counter_without_locking` still overshoots). Limits of the seam: no parallel work inside one unit of work (single connection); a nested scope that fails marks the whole unit faulted, so a swallowed exception cannot lead to a commit; a scope is closed when it ends and a straggling task cannot obtain it; the counter row lock is held until the whole operation commits, so capped operations of the same user serialize and operations touching different counters in opposite order can deadlock (keep units short). Convention: see CLAUDE.md, "Authorization".

## Revisit triggers (move to Cedar, or Casbin, behind the same interface)
Customers or support need to AUTHOR policies in a language (not pick profiles and limits); relationships/hierarchies (group inside group) that the flat profile model cannot express; a requirement for formal policy analysis; a Cedar .NET binding with a maintained, cached policy set and CI-proven macOS/Linux/Windows natives and a measured per-decision cost near 50 us.

## Consequences
- Easier: one door for every authorization question; engine swap is local; matrix coverage is enforced by a test; the cap cannot be overshot under concurrency (proved); the budget reservation is part of the business transaction, so a failed operation releases it and a retry cannot double count.
- Harder / accepted: we maintain the rules model; every capped decision must run inside `IUnitOfWork.ExecuteAsync` (the store throws otherwise); the counter lock is held for the whole business operation, which serializes capped operations of the same user and calls for short units.
- Callers (ticket 10 onward) run the decision, the state change and the outbox write in one `IUnitOfWork.ExecuteAsync`; a failure is expressed by throwing, which rolls all of it back.
- ~~The rules are in memory (`PolicySet`)~~ Superseded by "Persisted rules (built)" below: factory rules stay in code, each organization's own rules are read from the database on every decision. The `PolicySet` catalog argument is fed from the module catalog collected by the host (`ModuleCatalog`, `[PermissionCatalog]`).

## Alternatives considered
- Cedar as the engine: viable and correct on all contract cases; rejected for now on latency (about 1.1 ms measured), maturity of the .NET binding and the extra translation layer, with the revisit triggers above. Tested only through generated policies and without a Cedar schema; native policy authoring and schema validation were not evaluated.
- Casbin.NET: 5-11 us and mature, but string-typed policy columns and expression matchers make numeric limits clumsy and unsafe if policy text is ever tenant-editable; no multi-subject deny without one enforce per profile.
- Advisory locks or `SELECT .. FOR UPDATE` before an application-side compare: workable, but two statements and a lock protocol to keep right; the single conditional upsert is simpler and proved.
- OPA/Rego, Amazon Verified Permissions: not attempted; a separate process or a network hop per decision contradicts the single-process, no-new-infrastructure foundation.

## Persisted rules (built)
Plataforma base ticket 06 (spec 5.4.3 to 5.4.9), migration `0010`. Decided and built after the spike; the single door (`IAuthorizationEngine.DecidirAsync`) did not change.
- **Factory profiles stay in code** (`PoliticaDeFabrica`: `dono`, `conta`), not editable, only duplicable (copy, or follow the template). Custom profiles, their rules, assignments and individual overrides are tenant tables (`perfis`, `perfil_regras`, `usuario_perfis`, `usuario_regras`, exact RLS). A custom profile's key for the engine is its id; a person's overrides are one more private profile `usuario:<id>`, so the evaluator has no special case.
- **The engine reads rules through `IPolicySource`** (`PostgresPolicySource` = factory rules + the organization's persisted rules), on every decision, with no cache: a change is in force on the next decision. Cost accepted for now (one short read inside the unit of work in progress, or its own read transaction); a cache needs an invalidation story first.
- **Changes only through `GestaoDePerfis`**, one unit of work each, asking the same engine (`perfil:gerir`, `permissao:atribuir`). Anti-self-promotion (own assignment, own override, a profile the actor holds) and anti-escalation (`GrantGuard`: nobody hands on what they do not hold or hold less generously) are enforced there and audited as `permissao:negar-escalada`. A rule scoped to a unit must name a unit of the same organization (invalid otherwise, 400-class result, never a foreign-key 500).
- **Sessions follow rights:** database triggers bump `contas.versao_credencial` of every affected account on any change of rights, so the sessions of ADR-010 end on their next request (5.4.9). A change to the factory rules in CODE does not bump anything.
- **Simulator** (`SimuladorDePermissoes`) asks `DecidirAsync` for another person inside a unit of work that is rolled back; it never reserves a cap.
- Still open: no HTTP route manages profiles (the service exists and is tested), and the permissions `perfil:gerir`, `perfil:ver`, `permissao:atribuir` are declared in the catalog but no route asks for them yet.
