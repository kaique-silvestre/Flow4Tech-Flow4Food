# Identidade, sessoes, protecao de login, convites e Google

Detalhe de referencia, lido sob demanda a partir do indice em `CLAUDE.md`. Mantenha aqui o detalhe do tema; a raiz guarda so o que vale para todo agente.

## Identidade (plataforma base, ticket 03, spec 5.2, ADR-005)
- Module `Identidade` (own module, depends on no other: it needs only Kernel and the Data/Audit infrastructure). Tables `contas` and `credenciais` (migration 0007, tenant tables, exact RLS); `usuario_unidades.usuario_id` now has a composite FK to `contas`. Premise: ONE account belongs to ONE organization (e-mail unique platform-wide; operational user name unique inside the organization).
- Services (Application, singletons, `AddIdentidade`): `GestaoDeContas` (`CriarDonoAsync` the founder types their OWN password and exists ONLY in an organization with no accounts at all (lock on the organization row `FOR NO KEY UPDATE` + count in the same unit; otherwise `StatusCriacao.OrganizacaoJaIniciada`; callable only by a trusted flow such as the Control Tower, never a public route); `CriarOperacionalAsync` returns the temporary credential ONCE and it EXPIRES (`credenciais.temporaria_expira_em`, migration 0008; default 72 h, `Flow4Tech:Identidade:CredencialTemporariaHoras`; from `IClock`; an expired one is the same generic `FalhaDeAutenticacao` / `SenhaAtualInvalida`, after the same hashing work; changing the password clears it; only a reset, ticket 09, brings the account back; rows without a deadline never expire); `DesativarAsync`; `DefinirDonoAsync`, which only touches an ACTIVE account: `UPDATE ... AND ativa`), `TrocaDeSenha` (the person changes their own password, needs the current one), `Autenticacao` (returns `Autenticado`, `DeveTrocarSenha` or the single `FalhaDeAutenticacao`; issues no token and no session by itself: `POST /login` in Api passes its result to `Sessoes.IniciarAsync`, ticket 04). No API accepts another person's password. Authorization of WHO may call the admin methods is the route's job (`usuario:*`, tickets 05/06); the protection rules hold regardless (`ProtecaoDeConta`, pure: owner never deactivated/demoted by another, nobody edits their own permissions, always one owner, deactivating keeps all history).
- Secrets: the hash lives only in `credenciais`. `ContaParaLogin`, `PreAuthAccount` and `CredencialTemporaria` print a placeholder; never put them in a DTO, log or audit (`SensitiveData` refuses `hash`/`senha`/`credencial` keys: audit `After` uses `motivo`, `tipo`, `dono`...). `versao_credencial` grows on password change, deactivation and owner-flag change: every session carries the value it started with and stops working on the next request when it differs (ticket 04, "Sessões e tokens").
- Pre-authentication (before any organization context): ONLY through `IPreAuthLookup` -> `PreAuthDatabase` (Data; the single connection without context) -> the SECURITY DEFINER functions `identidade_localizar_por_usuario/_por_email` of migration 0007 (fixed `search_path`, EXECUTE only for `flow4tech_app`, exact key in, at most one row out, refuse to run inside an organization context, run UNDER RLS by setting the context to the asked organization; no BYPASSRLS role exists). Work that follows a login but precedes a session uses `OrganizationContext.WithoutUnit(organizationId)` with the organization taken from the account the lookup found; architecture test `PreSessionContextTests` allows it only in `Identidade/Application`.
- The ONE table without `organizacao_id`: `identidade_emails` (e-mail -> account), no RLS, NO privilege for `flow4tech_app`, read/written only by the SECURITY DEFINER functions; listed in `RlsArchitectureIntegrationTests.Exempt`. A new SECURITY DEFINER function must be added to the exact-set test `The_only_security_definer_functions_are_...` with its justification.
- Passwords: Argon2id (Konscious 1.3.1, 46 MiB/2/1 default, PHC string, rehash on login when parameters change), min 10 chars, max 256, NFKC, no symbol rules, `ICompromisedPasswordCheck` (local list + optional HIBP k-anonymity range, `Flow4Tech:Identidade:Hibp:Enabled`; default OFF). `Flow4Tech:Identidade:Hibp:IndisponivelRecusa` (default false) only matters with HIBP on: HIBP unreachable + option off = the password is accepted (local list still applies, warning logged); option on = refused with the typed result `VerificacaoIndisponivel` (`StatusCriacao` / `StatusTrocaDeSenha`; the check raises `VerificacaoDeSenhaIndisponivelException`, the services translate it). Raw password input above `PoliticaDeSenha.LimiteDeEntrada` (1024) is refused BEFORE NFKC and hashing in login, change and founder signup. Login: one generic failure, the same hashing work on every path (`VerifyDummyAsync`), response-time floor `Flow4Tech:Identidade:TempoMinimoDeLoginMs` (default 400). Failures of KNOWN accounts audit `autenticacao:falhar`; throttling and alerts: "Proteção de login" below.
- Tests that need a `usuario_unidades` row create the account first (`TestDatabase.InsertContaAsync`).

## Sessões e tokens (plataforma base, ticket 04, spec 5.3, ADR-010)
- Module: sessions live in `Identidade` (`Sessoes` in Application; `JwtEmissorDeTokens`, `PostgresSessaoStore`, `OutboxEventosDeSeguranca` in Infrastructure). Identidade stays independent: it learns the account's units through its own port `IUnidadesDaConta`, adapted in Api (`UnidadesDaContaAdapter`) over the Organizacao port.
- The session is a ROW (`sessoes`, migration 0009, tenant table, exact RLS, composite FKs to `contas`/`unidades`); the access token only names it. Per request `Sessoes.AutenticarAsync` checks signature/audience/exp (`IClock`), then the session row JOIN the account: not revoked, inside inactivity (default 12 h, slides, write at most once a minute) and absolute (default 14 days) limits, account active, `sessoes.versao_credencial = contas.versao_credencial = ver` of the token. So password change, deactivation, owner flag change, revoke, expiry take effect on the NEXT request; removing the user-unit link revokes the sessions working in that unit (trigger in 0009). A new permission/profile change (tickets 05/06) must bump `versao_credencial` or call `ISessaoStore.RevogarOutrasDaContaAsync`. Measured: ~4 ms p50 per check, no cache (ADR-010).
- Token: JWT HS256 (`Microsoft.IdentityModel.JsonWebTokens` 8.14.0), claims `sub`, `org`, `sid`, `ver`; audience = realm (`app`; `control` only reserved: its own key and audience, no route issues it); 5 min, 30 s skew; algorithm pinned, `none` refused. Keys ONLY from configuration: `Flow4Tech:Tokens:AppKey` (>= 32 bytes; rotate by moving it to `AppKeyPrevious`), `ControlKey`; the host does not start without `AppKey` outside Development/Testing (there a missing key makes an ephemeral one). Read from `Authorization: Bearer` only. Never write a key literal in code (`SessionDoorTests`).
- Refresh: opaque `r1.<org>.<256 bits>`, stored as SHA-256 only (`sessao_refresh`), rotated on every use; a used token presented again revokes the session, audits `sessao:refresh-reutilizado` and raises the outbox event `seguranca.refresh-reutilizado` (once per session). Two simultaneous refreshes with the same token: one wins, the other is a reuse and the session dies, so a client must refresh from a single place at a time. Cookie `__Host-f4t_refresh` (HttpOnly, Secure always, SameSite=Strict, Path=/), set by `RefreshCookie`. In plain-HTTP tests read `Set-Cookie`, assert, and replay it in a `Cookie` header.
- Routes: public `POST /login`, `POST /refresh`, `POST /logout` (allowlisted by method+pattern in `RoutePermissionTests.PublicWithoutSession`, each declares a `sessao:*` permission); `POST /sessao/trocar-senha`, `GET /sessoes`, `GET /sessoes/todas`, `POST /sessoes/{id}/revogar`. The three public routes carry `.RequireCsrfGuard()` (header `X-F4T-Csrf: 1`, own-authority/configured `Origin`, `Sec-Fetch-Site`) and every body-reading route `.WithBodyLimit(n)` (`RouteGuardsMiddleware`, 413). Login body names the typed organization `organizacaoDoLogin` (not a context field). One failure for login (401, empty body, no cookie).
- States: login with a temporary credential gives a session that reaches only `POST /sessao/trocar-senha` and `POST /logout` (403 elsewhere); the change revokes every other session of the account and returns a new normal one. With one linked unit it becomes active at login; with several or none the session starts without one (only the selection routes work). Other people's sessions: owner only for now (`sessao:ver-todas`/`sessao:revogar` are declared; ticket 05 turns it into `DecidirAsync`).
- Audit actions (`IdentidadeAuditActions`): `sessao:iniciar`, `sessao:encerrar`, `sessao:revogar`, `sessao:refresh-reutilizado` (+ `sessao:trocar-unidade`). Audit data never carries a key containing "senha"/"token": use `restrita`, `motivo`.
- Config (env, defaults): `Flow4Tech__Sessoes__InatividadeHoras` (12), `AbsolutaDias` (14), `IntervaloDeAtividadeSegundos` (60), `AllowedOrigins__0..` (none), `Flow4Tech__Tokens__AccessMinutos` (5). The clocks are layered settings since ticket 10 (see "Configurações em camadas"): the variables above are their SYSTEM layer.

## Proteção de login e alertas (plataforma base, ticket 08, spec 5.5)
- `Autenticacao` judges every attempt BEFORE any lookup or hashing with `ILimitadorDeLogin` (Application port; `LimitadorDeLoginEmMemoria` in Infrastructure): progressive lock per account AND per address (`base * 2^(failures - limit)` up to a ceiling), different limits for e-mail and operational accounts, credential stuffing (many accounts from one address; many addresses against one account), adaptive CAPTCHA. Thresholds: `LimitesDeLogin`, built from the system layer of the `bloqueio.*` settings (`Flow4Tech:Identidade:Bloqueio:*`, ticket 10). The key is the TYPED identifier, never the account found, so unknown names lock exactly like known ones; a blocked attempt does no hashing, is not audited, still waits the response-time floor, and answers `LoginBloqueado` (`POST /login` 429 + `Retry-After`) or `CaptchaExigido` (428). Overloads with `ContextoDeLogin(ip, captchaResposta)`; the ones without it count by account only.
- State is IN PROCESS memory (lost on restart, per instance, bounded at `MaximoDeRegistros`). Shared/general rate limiting is deliberately postponed (F4-0096, ADR-011 "Decision update"): it becomes mandatory before running a second API instance. Swapping it for a shared store means changing the port. An address has no organization: its lock goes to the technical log (`login.ip-bloqueado`, address only as an 8-hex digest). The address comes from `RemoteIpAddress`; behind Railway set `Flow4Tech__Rede__ProxyConfiavel=true` (last `X-Forwarded-For` entry, `ForwardLimit=1`; only safe if the API is reachable through the proxy alone).
- CAPTCHA: `ICaptcha` has no provider (`CaptchaNaoConfigurado`, `Configurado=false` = never asked). E-mail: `IEnviadorDeEmail`; `EnviadorDeEmailDeDesenvolvimento` keeps messages in memory and logs the subject only (never recipient or body). No e-mail really leaves until the provider (open question 4).
- Security events (outbox, same unit of work as the action): `seguranca.login-novo` (`Sessoes.CriarAsync` via `IAcessosConhecidos`: device = user agent without digits, place = network prefix IPv4 /24 / IPv6 /64, table `acessos_conhecidos`, migration 0012, max 50 per account and kind; the first login of an account only sets the baseline), `seguranca.conta-bloqueada` (+ audit `autenticacao:bloquear`, known accounts only), `seguranca.senha-trocada`, and the older `seguranca.refresh-reutilizado`. `AlertasDeSeguranca.Consumidores` turns the first three into e-mails to the person (if the account has an e-mail) and to the active owners; registered as `IOutboxConsumer` (idempotent on the event id). The dispatcher is still not in the DI nor scheduled, so nothing runs them in production yet.
- Tests: `LimitadorDeLoginTests`, `AutenticacaoProtegidaTests`, `ImpressaoDeAcessoTests` (no database); `AlertasDeSegurancaIntegrationTests` (PostgreSQL); `SessoesEndpointsTests.Repeated_failures_lock_...` (HTTP). Recovery without enumeration reuses the limiter (done in ticket 09, see below).

## Convites, recuperação e Google (plataforma base, ticket 09, spec 5.2.1, 5.2.3, 5.2.5, 5.2.6)
- Tokens de uso único (`TokenDeUso`): convite `c1.<org 32 hex>.<256 bits>`, recuperação `a1.<...>`; só o SHA-256 do texto inteiro é guardado (`convites`, `recuperacoes`, migração 0013, tenant, RLS exata). A organização no token é um LOCALIZADOR: a busca por hash roda sob a RLS dela, por isso não existe função SECURITY DEFINER nem tabela sem `organizacao_id` nova. O token só existe no e-mail (direto por `IEnviadorDeEmail` depois do commit, fragmento `#token=` no link; nunca no outbox, na auditoria ou no log; falha do provedor = `FalhaNoEnvioDeEmailException`, vira log sem endereço). Uso único por UPDATE condicional (`usado_em IS NULL AND expira_em > agora`), vencido/usado/revogado/desconhecido/malformado dão a mesma resposta.
- `Convites`: `ConvidarAsync` (`usuario:convidar`; um pendente por e-mail, novo revoga o antigo; só diz se o e-mail já é membro da PRÓPRIA organização), `RevogarAsync`, `AceitarAsync` (rota pública; a pessoa escolhe a PRÓPRIA senha; o e-mail só entra em `identidade_emails` ao aceitar). Perfil e unidade ficam no convite e vão no evento `identidade.convite-aceito`; aplicá-los é pendente e deve usar os direitos de quem convidou (`GestaoDePerfis`, GrantGuard).
- `RecuperacaoDeAcesso`: `SolicitarAsync` não devolve nada (rota: 202 sempre), espera o piso de tempo do login, conta cada pedido no `ILimitadorDeLogin` (chave `recuperacao:<e-mail>` + IP) e descarta em silêncio quando bloqueado; `RedefinirAsync` confere o token, depois a senha, consome atômico, troca a senha (versão da credencial + `IRevogacaoDeSessoes` encerram todas as sessões), limpa o bloqueio de login do e-mail, audita e publica `seguranca.acesso-recuperado` (e-mail à pessoa e aos donos). `GestaoDeContas.RedefinirAcessoAsync` (`usuario:redefinir-acesso`): nova credencial temporária só para conta operacional ativa, uma vez, prazo de 72 h, nunca a própria.
- Google (`ContasGoogle`, porta `IProvedorOidc`, `ProvedorOidcGoogle` real): código + PKCE S256, `state` e `nonce`, id token validado (RS256 fixo, `kid` do conjunto, emissor, audiência, validade pelo `IClock`, nonce), `sub` + `email_verified`. NUNCA cria conta; vínculo só pela pessoa logada com senha atual, e-mail do Google verificado e igual ao da conta (`identidades_externas`, FK composta com o tipo `email`: o banco recusa conta operacional; `UNIQUE (provedor, sub)`); entrar exige o `sub` vinculado; todo o resto é `GoogleNeutro`. Estado do vai e volta em cookie `__Host-f4t_oidc` (`SameSite=Lax`, assinado por `SeloDeTransacaoHmac`, chave derivada de `Flow4Tech:Tokens:AppKey`). Config: `Flow4Tech__Identidade__Google__ClientId|ClientSecret|RedirectUri`, `Flow4Tech__App__BaseUrl`, `ConviteDias`, `RecuperacaoMinutos`; sem ClientId as rotas dão 404. Testes: `ConvitesTests`, `RecuperacaoDeAcessoTests`, `RedefinicaoDeAcessoTests`, `ContasGoogleTests`, `ProvedorOidcGoogleTests` (sem banco, provedor falso, sem rede), `AcessoIntegrationTests` (PostgreSQL), `SessoesEndpointsTests` (HTTP).
- Rotas novas (públicas, em `RoutePermissions.PublicWithoutSession`): `POST /convites/aceitar`, `POST /recuperacao/solicitar|redefinir`, `GET /login/google`, `GET /login/google/retorno`; com sessão: `POST /convites`, `POST /convites/{id}/revogar`, `POST /contas/{id}/redefinir-acesso`, `POST|DELETE /conta/google/vinculo` (aceitam sessão sem unidade).
- `Bloqueio:*` é lido tarde (a fábrica do limitador pede ao `ISettings` quando o limitador é construído pela primeira vez), como as outras configurações.
